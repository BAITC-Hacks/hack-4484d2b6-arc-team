# Участник №2 — конструктор, рейтинг и кабинет бизнеса

Открыть `/ui#builder` на сервере FastAPI после `seed.py`. Оболочка Soft Retro и каталог участника №3 сохранены. Изменены только интерфейс, его документация и отдельная браузерная проверка; серверные модули и API-контракт не менялись.

## Реализовано

1. Выбор демонстрационного бизнеса из `GET /api/demo/profiles`, просмотр и повторное открытие его черновиков из `GET /api/tasks`. Все запросы задач используют `X-Demo-Business-Id`.
2. Большое поле описания и необязательная тема. `POST /api/tasks` создаёт задачу, `PATCH` сохраняет последующие изменения. Исходный текст остаётся в серверном `original_text`.
3. `POST /api/tasks/{id}/questions`: отображаются реальные тексты и ID вопросов сервера. Ответы допускают «не знаю» и пустые значения. Можно отдельно сохранить ответы или обновить вопросы.
4. `POST /api/tasks/{id}/generate-card`: все десять бизнес-полей редактируются; правки сохраняются через `PATCH proposed_card`. Рекомендации вынесены отдельно и не становятся обязательными требованиями. Повторная генерация требует согласия на замену текущей рабочей карточки.
5. `ai.message` и фактическая модель отображаются у соответствующего результата. Режим по умолчанию берётся из `/api/ai/status`; локальный режим явно подписан как шаблонный. При ошибке AI доступен отдельный переход в локальный режим, без скрытого переключения.
6. Блокировка повторных кликов и переключения профиля во время запроса. После успешного создания дальнейшие попытки используют сохранённый ID. Ответы, карточка и описание остаются в форме при сетевой ошибке, 422, ошибке AI и некорректном JSON. При `task_changed` сначала предлагается обновить сведения.
7. Правая панель отображает только `confirmed_rating`: балл, серверный уровень, семь категорий, вложенные начисления по полям и `missing_fields`. Нулевой подтверждённый рейтинг отличается от отсутствующего. Ссылки недостающих полей переводят к соответствующим редакторам. Клиент не содержит весов или собственной формулы.
8. После просмотра карточки пользователь ставит отметку проверки и нажимает «Сохранить и подтвердить». `POST /confirm` передаёт целиком текущую карточку и `expected_updated_at` из проверенной версии; сохранение и расчёт выполняет сервер одной транзакцией. Перед этим нет скрытого PATCH, способного замаскировать конфликт версий. Изменение поля или переключение задачи сбрасывает отметку проверки.
9. `POST /publish` вызывается отдельной кнопкой с версией из последнего ответа. Порог рейтинга отсутствует. Публикация блокируется до подтверждения текущих правок; для опубликованной задачи отображаются прежнее название и рейтинг опубликованного снимка, пока бизнес явно не обновит публикацию.

## Подтверждённые сведения и текущие правки

Локальные изменения и флаг сервера `has_unconfirmed_changes` помечают карточку как рабочую. Отображаемый балл, категории и недостающие поля продолжают относиться к последней подтверждённой версии; клиент не прогнозирует новый рейтинг. Обычное «Сохранить правки» не подтверждает и не публикует.

Несохранённые описание, тема или ответы сначала сохраняются отдельным действием. Эти исходные материалы не обновляют поля карточки автоматически: перед подтверждением нужно проверить, что карточка их отражает. Кнопка публикации использует `has_unpublished_changes`; статус `published` и уровень `draft` могут отображаться одновременно.

Ошибки `task_changed` и `confirmation_required` блокируют повторное подтверждение/публикацию до загрузки актуальной версии. Кнопка ошибки только обновляет сведения, сохраняя несохранённые поля. Подтверждение после обновления требует новой отметки проверки и отдельного нажатия. При сетевой ошибке прежний подтверждённый рейтинг остаётся на экране.

## Сохранение и восстановление

Неподтверждённые правки сохраняются в браузере отдельно для каждого бизнеса и задачи: `sana:builder:{businessId}:{taskId|new}`. Последняя открытая задача и выбранный бизнес запоминаются отдельно. При открытии загружается серверная версия, а несохранённые локальные поля остаются в форме. Серверные сохранения отмечаются только после успешного ответа.

Если localStorage недоступен, интерфейс сообщает об этом; правки сохраняются в памяти страницы отдельно для каждой задачи, а сохранение на сервере продолжает работать. Перезагрузка без серверного сохранения в таком режиме может потерять правки. При закрытии с несохранёнными изменениями браузер получает стандартный запрос предупреждения.

Это демонстрация с синтетическими данными, не production-авторизация. UI не хранит API-ключ и не делает запросов к провайдеру напрямую. Серверный и пользовательский текст выводится через `textContent` / `value`.

## Зависимости следующего этапа

- Публикация сохраняется в БД, но каталог и страница задачи в main пока используют статические примеры. Публичный API уже предоставлен отдельно в `feat/backend-workflow`; приватный `/api/tasks` не подставляется вместо публичного каталога.
- В `TaskCard` пока нет отдельного поля ожидаемого формата предложения (идея / прототип / готовое решение). Оно не добавлено односторонне: требуется общее расширение схемы.
- Интерфейс кабинета бизнеса (шаг 4) выполнен в `feat/business-ui`: список задач, переход к редактированию, сравнение откликов, ручные решения и подтверждение результатов этапов. Проверен с реальным сервером из `feat/backend-workflow` (`17678d0`) в отдельной сборке. В main изменения пока не объединены. Контракт и результаты описаны в [BUSINESS_DASHBOARD.md](BUSINESS_DASHBOARD.md); серверный контракт не изменён.

## Переход из кабинета в конструктор

`window.SanaBuilder` предоставляет внутренний интерфейс страницы: `initialized`, `context()`, `setBusiness(businessId)` и `open(businessId, taskId)`. Кабинет использует его для выбора бизнеса и открытия конкретной задачи. Перед переходом сохраняется локальная копия текущих правок; второй редактор и вторая копия состояния конструктора не создаются. Методы возвращают успешность запроса, не обходят серверную проверку владельца и не принимают готовые клиентские снимки задач.

## Проверки

Обычные серверные тесты:

```sh
.venv/bin/python -m pytest -q
```

Дополнительная браузерная проверка требует установленного Chromium/Chrome и совместимого ChromeDriver, но не Selenium:

```sh
# В отдельном терминале:
chromedriver --port=9515
# В корне репозитория:
.venv/bin/python tests/browser_builder.py --webdriver http://127.0.0.1:9515
```

Скрипт сам запускает приложение на свободном локальном порту с временной БД. Рабочая БД не меняется, API-ключ явно пустой, оплачиваемых вызовов нет. Скриншоты сохраняются в системном временном каталоге `sana-builder-screenshots` (можно задать `--screenshots`). Проверяются основной путь, неизвестные ответы, сохранение после перезагрузки, изоляция профилей, двойной клик, безопасный вывод текста, ошибки AI/422/сети, повтор и сохранность каталога. Дополнительный сценарий `tests/browser_readiness.py` вызывается тем же запуском: реальные рейтинги 0/55/80/100, публикация с 0, ссылки на поля, пересчёт вниз, ручная проверка, ошибки подтверждения и конкурирующие правки, сохранность опубликованного снимка. Это проверка интеграции и локального режима, не качества внешней модели.
