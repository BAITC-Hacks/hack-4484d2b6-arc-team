# Контракт API v0.4 — шаги 1–4

Базовый URL: `http://127.0.0.1:8000`. JSON в UTF-8, время в UTC ISO 8601.
ID — непрозрачные строки. В демоданных ID стабильны, новые задачи получают UUID.
Рабочие примеры запросов/ответов: `docs/api-examples.json`.
Схема реализованных операций: `/openapi.json`.

## Уже работает

| Метод | Адрес | Назначение |
|---|---|---|
| GET | `/health` | Проверка сервера и базы |
| GET | `/api/demo/profiles` | `{businesses: [], teams: []}` для переключателя |
| POST | `/api/tasks` | Создать черновик; ответ 201 и объект задачи |
| GET | `/api/tasks` | Массив задач выбранного бизнеса, не публичный каталог |
| GET | `/api/tasks/{id}` | Приватная рабочая задача выбранного бизнеса |
| PATCH | `/api/tasks/{id}` | Сохранить рабочие поля; ответ — объект задачи |
| GET | `/api/ai/status` | Режим по умолчанию, наличие конфигурации OpenAI и имя модели; без ключа |
| POST | `/api/tasks/{id}/questions` | Получить и сохранить минимум три вопроса |
| POST | `/api/tasks/{id}/generate-card` | Сохранить ответы и сформировать рабочую карточку |
| POST | `/api/tasks/{id}/confirm` | Подтвердить карточку и пересчитать рейтинг |
| POST | `/api/tasks/{id}/publish` | Опубликовать подтверждённый снимок без порога рейтинга |

Для операций бизнеса с черновиками и публикацией обязателен заголовок `X-Demo-Business-Id: business-1`
или `business-2`. Это выбор демопрофиля, не настоящий вход в систему.
Отсутствующий заголовок — 400, неизвестный профиль — 404. Чужая задача также даёт 404.
Операции команды используют `X-Demo-Team-Id: team-1`…`team-5`. Публичный каталог заголовков профиля не требует. Роли новых операций указаны ниже.

Создание принимает `original_text` (непустой, максимум 20 000 символов) и `topic`
(необязательный, максимум 100 символов). `business_id` определяется из заголовка.

PATCH принимает только `draft_text`, `topic`, `answers`, `proposed_card`.
Пропущенное поле не меняется. `answers` и `proposed_card` при передаче заменяются
целиком; пустые поля карточки имеют значение `""`, список рекомендаций — `[]`.
`null`, пустой PATCH, поля статуса, рейтинга, владельца или снимков отклоняются.
`answers` — объект `{question_id: answer}`. `questions` — массив `{id, field, text}`,
его заполняет операция `/questions`. Новые AI-запросы описаны ниже.

Поля карточки:

`title`, `context`, `need`, `users`, `data`, `constraints`, `expected_result`,
`success_criteria`, `contact`, `interaction_format`, `ai_recommendations`.

Все поля, кроме списка `ai_recommendations`, — строки. Рекомендации не являются
подтверждёнными требованиями бизнеса. Клиент не рассчитывает рейтинг.

Слои задачи:

- `original_text` — исходный ввод, не меняется.
- `draft_text`, `questions`, `answers`, `proposed_card` — рабочие материалы.
- `confirmed_card`, `confirmed_rating`, `confirmed_topic`, `confirmed_at` — последний подтверждённый снимок.
- `published_card`, `published_rating`, `published_topic`, `published_at` — снимок для общего каталога.
- `status` — только `draft` или `published`; это не уровень готовности.
- `questions_ai`, `card_ai` — источник последней генерации: `mode`, `model`,
  `message`, `generated_at`; до генерации — `null`. Ручное сохранение карточки
  через PATCH сбрасывает `card_ai`, поскольку её текст теперь отредактирован человеком.

До подтверждения рейтинг равен `null`: показывайте «Ещё не рассчитан», не 0.
После подтверждения сервер возвращает `score`, `level`, `categories`, `missing_fields`.
Категория содержит `key`, `label`, `points`, `maximum`, `fields`;
элемент `fields` — `{field, label, points, maximum}` для объяснения начислений.
`missing_fields` содержит имена полей карточки, за которые не начислены баллы.
Уровни: `draft` (0–39), `working` (40–69), `ready` (70–89), `priority` (90–100).
Полная [формула и ограничения](SCORING.md). Рекомендации AI не дают баллов.

Ошибки 400/404/405/409/422:

```json
{"error":{"code":"validation_error","message":"Проверьте поля запроса","details":[{"field":"body.original_text","message":"..."}]}}
```

Клиент должен сохранять локальный ввод при любом неуспешном запросе.
Для общего сервера CORS не нужен. Для разработки на другом порту задайте
`CORS_ORIGINS` в `.env` (примеры есть в `.env.example`).

## Подтверждение и публикация — работают

Оба POST требуют `expected_updated_at` из последнего полученного объекта задачи.
Передавайте его без изменения, включая часовой пояс. При конфликте — 409
`task_changed`: сохраните локальный ввод, загрузите актуальную задачу и предложите
пользователю проверить изменения. Не подтверждайте повторно автоматически.

`POST /api/tasks/{id}/confirm`:

```json
{
  "expected_updated_at": "2026-09-23T10:00:00Z",
  "proposed_card": {
    "title": "Учёт остатков",
    "context": "Учёт ведётся вручную.",
    "need": "Автоматизировать поиск дефицита.",
    "data": "Есть CSV на 500 товаров."
  }
}
```

`proposed_card` необязателен: без него подтверждается сохранённая рабочая карточка.
При передаче это полная замена карточки (пропущенные поля станут пустыми), а не PATCH.
`null` отклоняется. Название должно быть непустым и не заглушкой; остальные сведения
можно оставить пустыми. Сохранение карточки, расчёт и подтверждение — одна транзакция.
Тема берётся из текущего `topic`; изменить её можно через PATCH до подтверждения.
Ответ 200 — непосредственно объект задачи, без обёртки `task` из AI-операций.
Используйте `confirmed_rating` из ответа для панели рейтинга. Клиентский рейтинг,
статус или снимки в запросе запрещены. Подтверждение само по себе не публикует.

`POST /api/tasks/{id}/publish`:

```json
{"expected_updated_at": "2026-09-23T10:01:00Z"}
```

Время берётся из ответа **confirm**, а не из более ранней загрузки. Ответ 200 — задача.
Без подтверждения или при последующих изменениях карточки/темы — 409
`confirmation_required`. При публикации копируются подтверждённые карточка, тема
и рейтинг; `status` становится `published`. Порог рейтинга отсутствует, даже 0
допустим. Публичное чтение выполняется через `/api/catalog`; `/api/tasks` остаётся приватной рабочей областью бизнеса.

После редактирования опубликованной задачи старый снимок остаётся опубликованным.
Чтобы обновить его, снова выполните confirm → publish. `published_at` хранит время
первой публикации для стабильной сортировки; `updated_at` отражает последнюю запись.
Повтор действия с актуальной версией и без изменений не меняет данные и время.

Флаги в ответе:

- `has_unconfirmed_changes`: карточка/тема отличаются от подтверждённых либо подтверждения нет.
- `has_unpublished_changes`: есть подтверждённый снимок, отличающийся от опубликованного.

Они сравнивают снимки карточки, темы и рейтинга; изменения исходных рабочих
материалов (`draft_text`, вопросы, ответы) сами по себе не меняют карточку или баллы.
Перед подтверждением бизнес должен проверить сформированную карточку.
Готовый сценарий с ответами сервера: `docs/scoring-examples.json`.

## AI-конструктор — работает

`POST /api/tasks/{id}/questions` принимает необязательное тело `{"mode":"local"}`
или `{"mode":"openai"}`. Если режим не указан, используется `AI_MODE` сервера.
До вызова сохраните описание через POST/PATCH. Ответ: `{"task": {...}, "ai": {...}}`.
Полный объект задачи содержит обновлённые `questions` и `questions_ai`.
Идентификаторы имеют вид `q-data`, `q-users`; используйте ID из ответа, а не
фиксированные номера. При повторном запросе вопросы с непустыми ответами сохраняются.

`POST /api/tasks/{id}/generate-card` принимает:

```json
{"mode":"local","answers":{"q-data":"Есть тестовый CSV на 500 товаров."}}
```

`answers` необязателен: без него используются сохранённые ответы. Переданные
ответы объединяются с сохранёнными; пустая строка очищает конкретный ответ.
Неизвестный ID вопроса отклоняется с 422 до записи. Если вопросов ещё нет — 409.
Ответы сохраняются ДО обращения к модели, поэтому при отказе AI они не теряются.
Ответ также имеет вид `{"task": {...}, "ai": {...}}`, с обновлёнными
`proposed_card` и `card_ai`. Карточка остаётся рабочей; рейтинга и публикации нет.

В `ai` и сохранённых метаданных:

```json
{"mode":"local","model":null,"message":"Локальный режим: шаблонные вопросы и извлечение текста без внешней AI-модели.","generated_at":"2026-09-23T10:00:00Z"}
```

Показывайте пользователю `ai.message`; local нельзя выдавать за ответ OpenAI.
Для openai указан фактически использованный `model`. Метаданные относятся к
последней операции; вопросы с уже данными ответами могут сохраняться из предыдущей.

Ошибки AI используют прежний формат `error`, дополненный `local_mode_available: true`:

- 503 `ai_not_configured` — на сервере нет ключа;
- 503 `ai_unavailable` — недоступна сеть или API провайдера;
- 504 `ai_timeout` — истёк таймаут;
- 502 `ai_invalid_response` — неверный JSON, схема, число вопросов или неподтверждённые сведения;
- 502 `ai_incomplete` / `ai_refusal` — незавершённый ответ / отказ модели;
- 409 `task_changed` — задача изменена во время генерации; загрузите её снова.

Автоматического переключения на local нет: при ошибке покажите отдельное действие
«Продолжить в локальном режиме», повторяющее операцию с `mode=local`.
Вопросы и рабочая карточка при ошибке остаются прежними, новые валидные ответы
сохраняются. Исходный текст и подтверждённые/опубликованные снимки AI не изменяет.
Инструкции провайдера, ограничения локального режима и тестирование: [AI.md](AI.md).

## Каталог, отклики и этапы — работают

| Метод и адрес | Профиль | Результат |
|---|---|---|
| `GET /api/catalog?topic=retail&readiness=working` | Не нужен | Массив опубликованных задач |
| `GET /api/catalog/{id}` | Не нужен | Одна опубликованная задача |
| `POST /api/tasks/{id}/proposals` | Команда | Отправленное предложение |
| `GET /api/tasks/{id}/proposals` | Бизнес-владелец | Все предложения по своей задаче |
| `GET /api/my/proposals` | Команда | Только собственные предложения |
| `PATCH /api/proposals/{id}` | Бизнес-владелец задачи | Решение по одному предложению |
| `POST /api/proposals/{id}/milestones` | Выбранная команда | Отправленный результат этапа |
| `POST /api/milestones/{id}/confirm` | Бизнес-владелец задачи | Подтверждённый этап с баллами |

Все успешные операции этой таблицы возвращают 200. Заголовок бизнеса —
`X-Demo-Business-Id`, команды — `X-Demo-Team-Id`. ID берутся из `/api/demo/profiles`.
При отсутствии нужного заголовка — 400, неизвестном профиле — 404.
Запись другого владельца/команды возвращает 404, а не раскрывает чужие отклики.
Это изоляция по выбранному демопрофилю, не настоящая авторизация.

### Публичные задачи

GET возвращает **только** `id`, `topic`, `status`, `published_at`, `published_card`,
`published_rating`. `topic` берётся из `published_topic`, поэтому неподтверждённые
изменения темы не попадают в каталог. Исходный текст, вопросы, ответы, рабочая
карточка и неподготовленные правки не передаются. Черновик по публичному ID — 404.

Сортировка: балл по убыванию, затем время первой публикации и ID по возрастанию.
`topic` — точное совпадение с сохранённой темой, например `retail`, не её переводом.
`readiness` — `draft`, `working`, `ready` или `priority`; неверное значение — 422.
Фильтры комбинируются; отсутствие результатов — `[]`. Задачи с 0 баллов доступны.

Seed создаёт черновики, поэтому каталог новой БД пуст до первой публикации.
Браузерные страницы пока читают демонстрационный JSON: участник №3 заменяет источник
на эти GET. Сервер не подставляет тестовые записи при пустом каталоге или ошибке.
Для небольшого MVP список возвращается целиком; пагинация пока не предусмотрена.

### Предложения

Тело `POST /api/tasks/{id}/proposals`:

```json
{
  "idea": "Прототип учёта товаров",
  "plan": "Загрузить CSV, показать остатки и проверить дефицит",
  "timeline": "Две недели",
  "prototype_url": null,
  "questions": "Какие товары проверить в первую очередь?"
}
```

`idea`, `plan`, `timeline` обязательны и непусты; `questions` по умолчанию `""`.
`prototype_url` необязателен, `null` означает отсутствие прототипа. Если есть ссылка,
допускается только HTTP/HTTPS. Пустую строку ссылки интерфейс преобразует в `null`.
Строки ограничены 20 000 символами. ID команды, статус и время устанавливает сервер;
неизвестные поля запроса отклоняются с 422. На черновик откликнуться нельзя (404).

Ответы создания, решения и обоих списков содержат:
`id`, `task_id`, `team_id`, `idea`, `plan`, `timeline`, `prototype_url`, `questions`,
`status`, `created_at`, `decided_at`, **`team_name`, `task_title`, `milestones`**.
`task_title` — название из опубликованной карточки; `milestones` — массив результатов
этого предложения в порядке отправки. Полный вид задачи читается через публичный GET.

Одна команда отправляет одно предложение на задачу. Повтор с теми же нормализованными
полями возвращает существующее предложение и его актуальный статус; с другими —
409 `proposal_exists`. Изменение и отзыв отправленного предложения в MVP отсутствуют.

Тело `PATCH /api/proposals/{id}`:

```json
{"status":"selected"}
```

Допустимы `selected` и `rejected`. Решение принимается только из `submitted`.
Повтор того же решения возвращает прежний результат без смены времени; попытка
заменить уже принятое решение — 409 `decision_conflict`. Повторное открытие решения
не реализовано. Выбор одной команды **не меняет** остальные предложения; бизнес
может выбрать несколько, отклонить отдельные либо пока никого не выбирать.

### Этапы и баллы

Тело `POST /api/proposals/{id}/milestones`:

```json
{"description":"Прототип проверен на тестовом CSV","result_url":"https://example.test/demo"}
```

`description` — обязательная непустая строка до 20 000 символов, `result_url` —
необязательная HTTP/HTTPS-ссылка или `null`. Сервер не скачивает содержимое ссылки.
Только команда этого предложения со статусом `selected` может отправить результат;
свой ещё не выбранный или отклонённый отклик — 409 `team_not_selected`.

Ответ: `id`, `proposal_id`, `description`, `result_url`, `status`, `points_awarded`,
`created_at`, `confirmed_at`. До подтверждения: `status: submitted`, баллы 0.

`POST /api/milestones/{id}/confirm` принимает заголовок бизнеса, **тело не требуется**.
Первое подтверждение сохраняет `status: confirmed`, время и **10 баллов**.
Это правило нашего MVP из DEVELOPMENT_PLAN.md, а не шкала организаторов.
Повторное подтверждение возвращает тот же этап; баллы и время не изменяются.

Повтор отправки идентичных описания и ссылки в том же предложении возвращает
существующий этап, в том числе уже подтверждённый. Другой результат — новый этап,
который бизнес подтверждает отдельно. Редактирования и удаления этапов пока нет.
Защита повторов работает и при параллельных запросах: проверка и запись идут в одной
SQLite-транзакции. Идентификаторы запросов для повторов не требуются.

`GET /api/demo/profiles` дополнен `teams[].points`: суммой баллов подтверждённых
этапов команды по всем её предложениям. Отдельный изменяемый счётчик не хранится.
Сведения об этапах доступны в `milestones` владельцу задачи и своей команде через
списки предложений. Баллы команды не влияют на рейтинг задачи.

### Интеграция и проверка

Участник №2 использует список предложений своей задачи, PATCH решения и POST
подтверждения этапа. Участник №3 использует каталог, POST предложения, «Мои отклики»
и POST результата. Обновлять статус на экране нужно после успешного ответа сервера;
при ошибке сохранять ввод. Заголовок команды разрешён в CORS.

[workflow-examples.json](workflow-examples.json) содержит синтетические запросы и
реальные ответы сервера для пути от опубликованной задачи с 0 баллов до этапа с 10
баллами. Проверки: `python -m pytest tests/test_workflow.py -q`. Схема SQLite остаётся
версии 3: используются существующие таблицы, миграция и новые зависимости не нужны.
