# Сервер: шаг 1 — каркас и хранение

Ветка участника №1: `feat/backend`. Реализован только первый шаг: FastAPI,
SQLite, пять сущностей, демонстрационные профили и сохранение рабочих черновиков.
AI, формула рейтинга, подтверждение/публикация, отклики и баллы ещё не реализованы.

## Запуск

Python 3.12 или новее. Выполнять из корня репозитория.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe seed.py
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

`Copy-Item` нужен только при отсутствии собственного `.env`. Для запуска без тестов
можно установить `requirements.txt`. Активация окружения не обязательна.
В Linux/macOS использовать `.venv/bin/python` вместо `.venv\Scripts\python.exe`.

- `http://127.0.0.1:8000/health` — проверка сервера и БД.
- `http://127.0.0.1:8000/docs` — интерактивный API.
- `http://127.0.0.1:8000/openapi.json` — машинная схема работающих маршрутов.
- `http://127.0.0.1:8000/api/demo/profiles` — профили для переключателя.
- Главная страница пока возвращает JSON. HTML и стили добавят участники №2 и №3.

По умолчанию SQLite находится в `data/challenge_hub.sqlite3`. Относительный
`DATABASE_PATH` разрешается от корня проекта, независимо от рабочей директории.
`.env` читается автоматически; переменные окружения имеют приоритет.
База, окружение и секреты исключены из Git. Внешние сервисы и ключи на шаге 1 не нужны.

## Демонстрационные данные

```powershell
.\.venv\Scripts\python.exe seed.py
```

Создаёт два бизнеса (`business-1`, `business-2`), пять команд (`team-1`…`team-5`)
и пять черновиков (`draft-1`…`draft-5`). Все сведения синтетические.
Повторный запуск пропускает существующие ID и не затирает пользовательские изменения.
Seed выполняется транзакционно. Автоматического наполнения при старте сервера нет.

Участник №3 может подготовить другой JSON с теми же ключами:

```powershell
.\.venv\Scripts\python.exe seed.py --source fixtures/demo.json --database data/another-demo.sqlite3
```

На шаге 1 нет готовых опубликованных карточек и откликов: их наполнение появится
вместе с рейтингом и соответствующими операциями. Рейтинг черновика — `null`, не
выдуманный балл. Все ключи пустой рабочей карточки присутствуют.

## Хранение и границы ответственности

| Область | Файлы участника №1 |
|---|---|
| Сервер и маршруты | `app/main.py` |
| Настройки | `app/config.py`, `.env.example` |
| SQLite, схема v1 | `app/db.py`, `app/schema.sql` |
| Типы и статусы | `app/models.py` |
| Чтение и запись | `app/repository.py` |
| Наполнение | `seed.py`, `fixtures/demo.json` |
| Зависимости и проверки | `requirements*.txt`, `tests/test_storage.py` |
| Контракт для интерфейсов | `docs/API.md`, `docs/api-examples.json` |

`app/templates/` и `app/static/` зарезервированы за интерфейсами, сервер этот каталог
на шаге 1 не создаёт и не меняет. Soft Retro реализует участник №2.

Связи: бизнес → задачи; задача + команда → отклики; отклик → этапы.
База проверяет внешние ключи, допустимые статусы и наличие снимка при публикации.
В откликах нет уникальности по задаче: несколько команд могут быть выбраны позже.
Баллы будут храниться на подтверждённом этапе; рейтинг задачи — отдельные данные.
Проверка права отправки этапа, переходов статусов и однократное начисление — шаг 4.

Исходный текст неизменяем. Рабочий текст, вопросы, ответы и `proposed_card`
хранятся отдельно от `confirmed_card` и `published_card`. Рейтинги тоже разделены
на подтверждённый и опубликованный снимки. Обычное сохранение не меняет эти снимки.
`PRAGMA user_version=1` фиксирует версию схемы; будущие изменения потребуют миграции,
а не удаления базы. WAL, внешние ключи и транзакции включены.

Переключатель демопрофиля не является авторизацией: любой пользователь может
выбрать известный ID. Рабочие маршруты фильтруют задачи по выбранному владельцу,
но этот сервер предназначен для локальной демонстрации с синтетическими данными.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Проверяются повторное наполнение, откат транзакций, внешние ключи, сохранение после
перезапуска, изоляция снимков, выбор владельца и ошибки валидации без потери текста.
Тесты используют временные базы и не изменяют демонстрационную БД.
